# ZXCode 纵深防御安全检查规格

## 背景

ZXCode 已经有工具执行、路径限制、确认弹窗和 plan-only 拦截，但这些防线是分散的：有的在工具内部，有的在调度层，有的只覆盖单一场景。随着功能继续增加，仅靠局部检查不够，容易出现“某个入口忘了拦，另一个入口还在放行”的漏洞。

这一章要做的是一套纵深防御的安全检查机制，把高危操作挡在执行前，把路径和参数限制收紧，再把边界不明确的情况交回用户决定。第一版只覆盖最容易出事的写入和执行类工具。

## 目标用户

- 需要在 ZXCode 里安全执行文件写入和 shell 命令的开发者。
- 希望把危险操作、路径沙箱和人工确认统一起来，而不是散落在各个工具里的维护者。
- 希望对高频合法操作做永久放行，但又不想把规则做得太宽的用户。

## 能力清单

- 在工具执行前拦截已知高危 shell 命令和远程脚本直执行模式。
- 对文件读写和 shell 相关工具做路径沙箱，限制其活动范围在允许目录内。
- 提供可配置的 allow / deny / ask 规则，按工具、参数或路径模式生效。
- 提供三档全局权限模式：严格、默认、放行。
- 对规则未明确命中的操作走 HITL，支持本次允许、本会话允许、永久允许。
- 支持规则优先级：会话级临时规则 > 项目级固定规则 > 用户全局默认。
- 永久允许写回项目安全配置文件，形成可追踪的持久规则。
- 第一版只覆盖 `Bash`、`WriteFile`、`EditFile`，不把全量工具都纳入。

## 非功能要求

- **安全性**：高危操作必须至少经过一层硬拦截，不能只靠提示词。
- **可解释性**：每次拦截或询问都要给出可读原因。
- **可维护性**：规则应集中管理，不在各个工具内部重复堆逻辑。
- **可审计性**：永久允许必须写回项目配置，便于追踪和复现。
- **可扩展性**：以后新增工具时，可以接入同一套策略引擎。
- **最小范围**：第一版不扩到所有内置工具，不做外部安全服务。

## 设计骨架

### 策略分层

系统分成两层防线。

第一层是调度层预检，负责在工具执行前根据规则表决定 allow / ask / deny。它面向工具名、参数、路径模式和权限模式做统一判断，并负责把需要人工确认的情况交回界面。

第二层是工具内兜底，负责在真正执行文件系统或 shell 动作前再次检查路径、命令形态和权限边界。这样即使某个调度入口漏掉，工具本身也不会裸奔执行。

### 规则来源

规则来自四个层级，优先级固定。

最高层是会话级临时规则，只在当前会话内有效。其下是项目级固定规则，来自根目录的安全配置文件。再下是用户全局默认规则。最底层是模式本身，也就是严格、默认、放行三档全局姿态。

### 全局模式

严格模式表示除明确允许外都拒绝。默认模式表示未命中规则就询问用户。放行模式表示未命中规则直接放行，但硬黑名单仍然拦截。

### HITL

当规则没有明确命中，系统把决定权交回用户。用户可以选择本次允许、本会话允许或永久允许。永久允许会写回项目安全配置，但第一版只写精确命令签名或精确路径签名，不做模式扩散。

### 硬黑名单

黑名单只负责明确高危、无需争辩的操作，例如破坏性 shell、远程脚本直执行、明显越权路径、明确危险的覆盖写。黑名单先于模式和普通规则生效。

### 规则表达

规则第一版支持按工具名、命令签名、路径签名和参数模式匹配。为了避免误伤，永久允许优先落到精确签名，不把宽泛模式直接写成长期例外。

## 完成定义

- 有一个项目级安全配置文件可以承载规则。
- `Bash`、`WriteFile`、`EditFile` 已接入统一策略判断。
- 调度层与工具层都能拦截高危操作。
- 三档全局模式生效，并且含义清晰可测。
- 规则未命中时会询问用户。
- 用户可以把一次批准升级为本会话允许或永久允许。
- 永久允许会写回项目配置文件。
- 规则优先级按会话级、项目级、用户全局、模式的顺序工作。
- 端到端测试能覆盖拒绝、询问、临时允许和永久允许。

## Out of Scope

- 不覆盖全部六个内置工具，先只做 `Bash`、`WriteFile`、`EditFile`。
- 不实现外部安全服务或独立守护进程。
- 不做复杂的策略 DSL 或规则编译器。
- 不做长期学习、自动扩展或模型自己发明规则。
- 不把永久允许自动扩散成相似命令。
- 不做跨项目共享的云端规则同步。
