# ZXCode Agent 循环规格

## 背景

ZXCode 已经具备 OpenAI-compatible 流式对话、六个内置工具、统一工具执行器和一版能跑通的工具调用循环。但现有循环把"推理—行动—观察"的过程直接编码成一个只向终端吐文本增量的异步生成器：外层只能看到文本和一个完成对象，看不到模型在想什么、正在调哪个工具、工具跑了多久；循环的终止判断散落在流程里，没有显式状态；取消依赖 Textual worker 的强制撤销，中断后本轮已经完成的工具结果被整体丢弃；也没有任何办法让模型"只看不动"地先给出一份计划。

本章把循环本体重构成一个显式的 ReAct 状态机，并用事件流把全过程对外暴露，让终端界面、命令行和日志成为同一份事件的不同消费者，同时补上 plan-only 安全态与协作式取消。

## 目标用户

- 在终端里使用 ZXCode 完成多步编码任务、需要看清模型每一步在做什么的开发者。
- 想在真正改动文件之前先拿到一份行动计划并自行审批的用户。
- 需要在长任务中途安全打断，且不希望打断后会话历史错乱的用户。
- 在 ZXCode 之上接别的前端（纯 CLI、日志采集、自动化脚本）的二次开发者。

## 目标

- 用一轮 = 调 LLM → 解析响应 → 有工具就执行 → 结果回填 → 下一轮的 ReAct 范式承载循环本体，无工具调用即结束。
- 把循环的每一步都作为事件吐出，让上层按需消费，循环本身不感知任何界面。
- 用显式状态机管理轮次推进与终止，让"为什么停下来"始终有一个可读的原因。
- 让读类工具在同一轮内并发、写类工具串行，并在执行前后留出统一拦截位。
- 提供 plan-only 开关，进入后写类工具一律拦截，收尾给出计划与被拦截清单。
- 让循环随时响应外部取消，打断后会话历史仍然结构完整、可继续对话。

## 能力清单

### 循环本体

- Agent 循环按 ReAct 范式逐轮推进，一轮包含调用模型、解析响应、执行工具、结果回填四个阶段。
- 模型响应中不含工具调用时，循环把本轮文本作为最终回复结束。
- 循环把每轮产生的 assistant 消息与 tool 消息按调用标识成对追加进对话历史。
- 循环复用现有工具注册表导出的工具定义构造每一轮请求。
- 循环使用最小可用系统提示词，只说明助手身份与工具使用方式。

### 事件流

- 循环通过一个异步事件通道对外单向广播事件，不等待消费者处理。
- 通道提供异步迭代消费方式，同一份事件可被多个消费者转发。
- 事件覆盖用户消息、模型思考、模型文本、工具调用开始、工具调用结束、工具结果、一轮结束、最终回复、错误、取消、循环结束。
- 每个事件携带类型、时间戳、所属轮次和类型特定数据。
- 模型流式文本按增量逐条发出，让上层保持逐字渲染体验。
- 循环结束后通道关闭，消费者的迭代自然终止，不需要额外的哨兵约定。

### 状态机与终止

- 循环维护显式状态：空闲、运行中、工具执行中、只规划、已取消、已终止。
- 非法状态转换被拒绝并抛出可识别的异常，避免状态错乱。
- 终止路径包括：模型显式结束、本轮无工具调用、达到最大轮数、用户取消、不可恢复错误。
- 循环继续复用现有终止守卫，把重复观察、重复错误、无进展作为额外终止原因。
- 每次终止都携带一个终止原因，随一轮结束事件与循环结束事件一并发出。

### 工具执行

- 同一轮的多个工具调用按读写属性分组，读类并发执行，写类在读类全部结束后按模型给出的顺序串行执行。
- 每个工具调用在执行前经过前置拦截位，在执行后经过后置拦截位。
- 前置拦截位本章只实现 plan-only 检查，权限规则留空但保留调用点。
- 每个工具调用发出开始与结束事件，结束事件包含耗时与成功、失败、超时三种状态之一。
- 单个工具的失败、超时或参数错误转换为结构化结果回填给模型，不终止循环。

### plan-only 模式

- 用户可以通过斜杠命令进入和退出 plan-only 模式，模式状态在会话中保持。
- plan-only 下读类工具正常执行，写类工具被拦截并返回提示用户关闭开关的说明。
- plan-only 下的循环收尾时，把模型的自然语言计划连同本轮所有被拦截的写类调用清单一并交还用户。
- 被拦截的调用清单记录工具名、参数和拦截原因。

### 取消与超时

- 循环接受一个外部取消令牌，在每轮开始前、模型调用中、工具批次之间检查取消。
- 取消采用协作式语义：不强制终止正在执行的工具，等待其自行完成或超时。
- 取消发生时，已经完成的 assistant 与 tool 消息成对提交进会话历史；尚未拿到结果的工具调用补齐一条取消结果，保证每个调用标识都有配对的工具消息。
- 模型调用与单个工具执行各自有超时；模型调用超时终止循环，工具超时只影响该次调用。

## 非功能要求

- **状态一致性**：任何终止路径（正常、取消、错误、轮数上限）结束后，对话历史中每个 assistant 工具调用都必须有配对的 tool 消息，不允许悬空调用。
- **解耦**：循环模块不导入任何终端界面模块；界面只通过消费事件和读取最终结果与循环交互。
- **响应性**：事件发射不得阻塞循环推进；终端在工具并发执行和模型流式输出期间保持可刷新、可取消。
- **可观测性**：事件足以还原一次完整运行的时序，包含工具耗时与终止原因；不得记录 API Key 或完整敏感内容。
- **安全边界**：plan-only 下不得有任何写类工具真正执行；拦截发生在工具 execute 之前。
- **兼容性**：不改变现有工具契约、注册表、执行器的对外语义，不引入新的运行时依赖。
- **可测试性**：循环、状态机、事件流、plan-only、取消均可用伪造模型流与临时目录在无头环境下验证，不依赖真实 API。
- **无回归**：既有纯文本对话、工具调用、快捷键、斜杠命令与授权弹窗行为保持不变。

## 设计骨架

### 事件与通道

事件是一个不可变数据结构，承载类型、时间戳、轮次与类型特定负载。通道基于异步队列实现，循环侧只负责发射，消费侧通过异步迭代取事件；循环结束时关闭通道使迭代终止。通道不解释事件语义，也不承担渲染、日志或持久化职责。

### 循环与状态机

状态机是一个独立的小组件，只回答"当前处于什么状态"和"这个动作是否合法"，并记录终止原因。循环持有状态机、模型客户端、工具注册表、执行器、取消令牌和运行配置，负责按轮推进并在每个阶段边界发射事件。终止判断集中在轮末一处：先看模型是否给出工具调用，再询问现有终止守卫，最后检查轮数与取消。

### 工具批次与拦截位

工具批次执行沿用现有执行器的读写分组语义，在其之上包一层负责事件发射与拦截的调度层：对每个调用先过前置拦截，通过后发出开始事件、交给执行器、计时、发出结束事件，再过后置拦截。plan-only 检查是前置拦截的唯一实现；权限检查保留一个明确的空实现位置。

### plan-only

plan-only 是循环配置上的一个布尔开关，通过界面斜杠命令切换。开关打开时，调度层在前置拦截处把所有写类调用替换为一条带说明的失败结果并记入拦截清单，模型据此调整策略，最终以自然语言给出计划。循环收尾时把拦截清单附在最终结果上一并交还上层，本章不做计划落盘。

### 取消语义

取消令牌是线程安全的标志位加一个可等待的事件。循环在每轮开始、模型流消费过程中和工具批次之间检查；模型流通过关闭流来中断，工具批次不打断，等待其完成或触发自身超时。取消后循环走统一的收尾路径：补齐悬空工具调用的结果、提交已完成消息、发射取消与循环结束事件。

### 终端接入

终端界面从"消费文本增量"改为"消费事件"：文本增量事件继续追加渲染，工具事件渲染为可见的工具状态行，错误与取消事件渲染为状态提示，最终回复事件决定提交进会话的内容。取消不再依赖强制撤销 worker，改为触发取消令牌并等待循环自行收尾。plan-only 由一条新的斜杠命令切换，状态栏显示当前是否处于该模式。

## 完成定义

- 循环以状态机 + 事件流形式重写，终端界面完全通过事件驱动渲染。
- 一次运行的事件序列能够完整还原时序：用户消息、思考、文本、工具开始、工具结束、工具结果、轮结束、最终回复、循环结束。
- 五类终止路径均可触发并在事件中带出可读的终止原因。
- 同一轮内多个读类工具确实并发执行，写类工具确实在读类之后串行执行。
- plan-only 下写类工具零执行，收尾能拿到计划文本与拦截清单。
- 取消后会话历史中不存在悬空的工具调用，且可以直接继续下一轮对话。
- 既有测试全部通过，无行为回归。
- `docs/agent-loop/checklist.md` 中所有验收项均可观察并勾选。

## Out of Scope

- 复杂的系统提示词组装、分层指令、动态上下文注入；本章只用最小可用系统提示词。
- 完整的权限策略与规则配置语言；本章只保留拦截位与 plan-only 一条规则。
- 把 Agent 当作工具递归调用、子任务委派、多 Agent 协作。
- 计划的结构化 JSON 输出、计划落盘、计划审批后自动重放。
- 长期记忆、上下文压缩、会话持久化与跨进程恢复。
- 动态工具注册、插件发现、第三方工具加载。
- 事件的持久化、跨进程传输与远程订阅。
- 新增内置工具或修改现有六个工具的行为与授权策略。
