# 任务文档 1：全局指令模块化与优先级拼装

## 1. 任务背景

当前全局指令内容庞杂，身份设定、行为约束、工具使用、安全边界、代码规范、任务模式和输出风格等职责混在同一段系统指令中。随着后续章节或功能不断增加，直接在全局指令中插入新内容会导致维护困难、冲突难排查、缓存复用率下降，并且不利于验证不同指令块对模型行为的影响。

本任务旨在将全局指令按职责拆分为多个可组合模块，并通过优先级排序机制完成拼装，使系统指令具备清晰结构、稳定扩展能力和可测试性。

## 2. 任务目标

1. 将全局指令拆分为职责明确的模块。
2. 为不同模块定义优先级、加载顺序和冲突处理规则。
3. 设计模块拼装机制，支持后续章节或功能以模块形式插入。
4. 明确哪些规则应同时出现在全局指令和工具描述中，以强化关键行为。
5. 形成可用于实现和评估的模块化指令设计方案。

## 3. 范围说明

### 3.1 包含范围

- 全局指令职责拆分。
- 模块优先级设计。
- 模块拼装顺序设计。
- 模块冲突处理策略。
- 关键规则的双重强化策略。
- 指令模块的命名、元数据和版本字段设计。

### 3.2 不包含范围

- 不实现具体模型 API 调用逻辑。
- 不进行大规模自动化评测。
- 不修改实际线上系统配置。
- 不处理对话历史压缩或动态环境注入，这部分由后续任务文档负责。

## 4. 模块拆分建议

建议将全局指令至少拆成以下模块：

| 模块 | 职责 | 稳定性 | 优先级建议 |
|---|---|---:|---:|
| 身份模块 | 定义助手身份、产品身份、角色边界 | 高 | P10 |
| 安全边界模块 | 法律合规、隐私、危险操作、不可绕过规则 | 高 | P0 |
| 行为准则模块 | 做事风格、主动性、提问原则、任务完成标准 | 中高 | P20 |
| 工具使用模块 | 工具调用优先级、读写约束、专用工具优先规则 | 中高 | P15 |
| 代码规范模块 | 编码风格、测试要求、运行时选择、文件操作要求 | 中 | P30 |
| 任务模式模块 | Craft / Plan / Ask 等模式差异 | 中 | P40，可动态注入 |
| 输出风格模块 | 语言、格式、详细程度、交付规范 | 中 | P50 |
| 结果展示模块 | 产物交付、文件展示、最终回复要求 | 中高 | P25 |
| 记忆与长期上下文模块 | 工作记忆写入、项目记忆和用户记忆边界 | 中 | P35 |

优先级数值越小，约束越强。安全边界类规则必须始终高于其他模块。

## 5. 模块元数据设计

每个模块建议包含以下元数据：

```yaml
id: safety.boundary
name: 安全边界模块
priority: 0
stability: stable
cacheable: true
version: 1.0.0
depends_on: []
conflicts_with: []
injection_scope: global
```

字段说明：

- `id`：模块唯一标识。
- `priority`：模块优先级，用于排序和冲突解决。
- `stability`：`stable`、`semi_stable` 或 `dynamic`。
- `cacheable`：是否适合进入可缓存通道。
- `depends_on`：该模块依赖的其他模块。
- `conflicts_with`：可能产生冲突的模块。
- `injection_scope`：注入范围，如 `global`、`session`、`turn`、`tool`。

## 6. 拼装规则

### 6.1 基本顺序

推荐拼装顺序：

1. 安全边界模块。
2. 产品身份与角色模块。
3. 工具使用模块。
4. 行为准则模块。
5. 结果展示与交付模块。
6. 记忆与上下文模块。
7. 代码规范模块。
8. 任务模式模块。
9. 输出风格模块。
10. 当前会话动态补充模块。

### 6.2 冲突处理

当模块之间出现冲突时，按照以下顺序处理：

1. 安全边界优先。
2. 用户当前明确任务优先于默认偏好，但不能覆盖安全规则。
3. 专用工具规则优先于通用行为规则。
4. 更具体的规则优先于更宽泛的规则。
5. 同级规则冲突时，以优先级数值较小者为准。
6. 仍无法判断时，向用户提问或进入保守模式。

## 7. 关键规则双重强化

部分规则需要同时出现在全局指令和工具自身描述中，以覆盖模型默认偏好并减少误调用：

| 规则 | 全局指令位置 | 工具描述位置 | 目的 |
|---|---|---|---|
| 优先调用专用工具而非通用 shell | 工具使用模块 | Bash / 搜索 / 读写工具描述 | 避免模型习惯性使用 shell |
| 编辑文件前必须先读取 | 工具使用模块 | Edit / Write 工具描述 | 防止覆盖未知内容 |
| 文件产物必须展示给用户 | 结果展示模块 | 文件展示工具描述 | 避免生成后不交付 |
| 不递归删除个人目录 | 安全边界模块 | Shell / 文件操作说明 | 防止高风险误删 |
| 复杂任务需任务拆解 | 行为准则模块 | 任务管理工具描述 | 提高执行可追踪性 |

## 8. 实施步骤

1. 盘点现有全局指令，标记每段内容的职责类别。
2. 按职责拆分成独立模块，并补齐模块元数据。
3. 为每个模块设置优先级和稳定性标签。
4. 建立拼装器，按优先级和依赖关系生成最终系统指令。
5. 将关键规则同步写入相关工具描述。
6. 准备冲突样例，验证安全边界、工具优先和输出规则是否按预期生效。
7. 输出模块清单、拼装顺序表和冲突处理说明。

## 9. 验收标准

- 至少完成身份、行为、工具使用、代码规范、安全边界、任务模式、输出风格七类模块拆分。
- 每个模块都有唯一 ID、优先级、稳定性和注入范围。
- 拼装顺序清晰，可解释为什么安全和工具规则位于前部。
- 能支持后续章节以新模块方式插入，而不是直接修改整段全局指令。
- 至少列出 5 条需要双重强化的关键规则。
- 有明确的冲突处理规则和示例。

## 10. 风险与注意事项

- 模块拆得过细会增加拼装复杂度，应避免每条规则都独立成模块。
- 优先级设计不清晰会导致冲突难以解释。
- 动态内容误放入稳定模块会降低缓存命中率。
- 工具描述和全局指令重复时，要保证表述一致，避免细节冲突。

## 11. 预期交付物

1. 全局指令模块清单。
2. 模块元数据规范。
3. 模块拼装顺序说明。
4. 冲突处理规则说明。
5. 关键规则双重强化表。
