# 任务文档 2：稳定内容缓存与动态上下文通道

## 1. 任务背景

在多轮对话系统中，全局指令、工具描述、环境信息、对话历史和动态补充经常被混合放入同一上下文。由于工作目录、时间、操作系统、Git 状态、运行模式等信息会频繁变化，如果这些变化内容与稳定全局指令绑定在一起，就会导致缓存失效，增加调用成本和延迟。

本任务旨在区分稳定内容和变化内容，将稳定的全局指令与工具描述放入可缓存通道，将变化的环境信息、对话历史和动态补充放入对话通道，从而提高缓存命中率，并减少无关变化对系统提示缓存的破坏。

## 2. 任务目标

1. 建立稳定内容与动态内容的分类标准。
2. 设计可缓存通道与对话通道的职责边界。
3. 将环境信息从全局指令中迁移到对话首条系统级补充消息。
4. 定义环境信息的结构化格式。
5. 制定缓存命中验证方案。
6. 降低动态变化对全局指令缓存的影响。

## 3. 内容分类标准

### 3.1 稳定内容

稳定内容适合进入可缓存通道，包括：

- 产品身份与助手基础身份。
- 长期安全边界。
- 工具列表与工具参数描述。
- 通用工具使用原则。
- 长期代码规范。
- 长期输出规范。
- 不随单个会话变化的行为准则。

### 3.2 半稳定内容

半稳定内容可以缓存，但需要版本化管理，包括：

- 用户长期偏好。
- 项目长期约定。
- 专家包或技能说明。
- 固定业务流程。
- 固定评测标准。

半稳定内容应通过版本号或内容哈希控制缓存更新。

### 3.3 动态内容

动态内容不应放入全局可缓存指令，包括：

- 当前工作目录。
- 操作系统和 shell 信息。
- 当前时间。
- Git 分支、Git 状态、最近提交。
- 当前轮用户输入。
- 最近对话历史。
- 当前模式开关。
- 外部工具临时上线或下线提醒。
- 本轮临时补充约束。

## 4. 通道设计

| 通道 | 内容类型 | 是否缓存 | 更新频率 | 示例 |
|---|---|---:|---:|---|
| 全局可缓存通道 | 稳定全局指令、工具描述 | 是 | 低 | 安全边界、工具 schema |
| 半稳定缓存通道 | 项目约定、用户长期偏好 | 可选 | 中 | 项目规范、长期偏好 |
| 对话系统补充通道 | 环境信息、模式状态、动态提醒 | 否 | 高 | 工作目录、时间、Git 状态 |
| 对话历史通道 | 用户与助手历史消息 | 否或摘要缓存 | 高 | 最近 N 轮对话 |
| 工具结果通道 | 工具调用返回内容 | 否 | 高 | 文件读取结果、命令输出 |

## 5. 环境信息迁移方案

### 5.1 迁移原则

环境信息不应写入全局指令正文，而应作为每次会话开始时的系统级补充消息注入。这样可以确保环境变化不会影响稳定全局指令缓存。

### 5.2 环境信息字段

建议环境补充消息包含：

```yaml
environment:
  cwd: "E:/project/example"
  os: "win32"
  shell: "bash"
  ide_theme: "light"
  current_time: "2026-07-26T15:46:35+08:00"
  git:
    branch: "main"
    status_summary: "clean"
    last_commit: "optional"
  runtimes:
    python: "3.13.12"
    node: "22.22.2"
```

### 5.3 注入位置

推荐注入顺序：

1. 可缓存全局指令。
2. 可缓存工具描述。
3. 会话首条系统级环境补充消息。
4. 对话历史摘要或最近消息。
5. 当前用户输入。
6. 本轮动态补充提示。

## 6. 缓存策略设计

### 6.1 缓存键组成

建议缓存键只包含稳定内容：

- 全局指令模块集合版本。
- 工具描述集合版本。
- 半稳定项目规则版本。
- 半稳定用户偏好版本。

不应包含：

- 当前时间。
- 工作目录。
- Git 状态。
- 最近对话内容。
- 当前任务模式开关。

### 6.2 版本控制

每个稳定模块应有版本号。只有模块内容变化时才更新版本号。

示例：

```yaml
cache_bundle:
  global_instruction_version: "2026.07.1"
  tool_schema_version: "2026.07.1"
  project_memory_hash: "sha256:..."
  user_preference_hash: "sha256:..."
```

## 7. 缓存命中验证方案

通过解析 API 返回的缓存命中字段验证策略是否有效。建议记录以下指标：

| 指标 | 含义 |
|---|---|
| cached_tokens | 本次请求命中的缓存 token 数 |
| input_tokens | 本次请求总输入 token 数 |
| cache_hit_rate | cached_tokens / input_tokens |
| cache_miss_reason | 缓存未命中的推测原因 |
| stable_bundle_hash | 稳定内容哈希 |
| dynamic_payload_hash | 动态内容哈希 |

### 7.1 验证场景

准备以下请求进行对比：

1. 仅当前时间变化。
2. 仅工作目录变化。
3. 仅 Git 状态变化。
4. 仅用户输入变化。
5. 工具描述变化。
6. 全局指令模块变化。
7. 动态补充消息变化。

预期结果：

- 场景 1-4 和 7 不应导致稳定全局指令缓存失效。
- 场景 5-6 会导致对应稳定缓存块失效。

## 8. 实施步骤

1. 盘点当前上下文中所有内容，标记为稳定、半稳定或动态。
2. 将稳定内容拆入可缓存通道。
3. 将环境信息从全局指令中移出，改为会话首条系统级补充消息。
4. 设计结构化环境消息格式。
5. 为稳定模块和工具描述建立版本号或哈希。
6. 在请求日志中记录缓存命中字段。
7. 用典型场景验证缓存策略是否生效。
8. 根据缓存命中情况调整模块边界。

## 9. 验收标准

- 明确列出稳定、半稳定和动态内容分类。
- 环境信息不再出现在全局指令正文中。
- 当前时间、工作目录、Git 状态变化不会导致稳定全局指令缓存失效。
- 可以通过 API 返回字段计算缓存命中率。
- 至少完成 7 组典型场景的人工对比。
- 有缓存 miss 的定位方法。

## 10. 风险与注意事项

- 如果工具描述频繁变化，会影响工具 schema 缓存，应控制工具版本发布频率。
- 用户长期偏好既可能稳定也可能变化，需要版本化而不是硬编码。
- 对话历史过长时，应考虑摘要，但摘要本身属于动态内容。
- 环境信息虽然动态，但仍应具备明确结构，避免模型误解。

## 11. 预期交付物

1. 稳定 / 半稳定 / 动态内容分类表。
2. 缓存通道与对话通道设计说明。
3. 环境信息结构化补充消息格式。
4. 缓存键与版本管理方案。
5. 缓存命中验证场景清单。
